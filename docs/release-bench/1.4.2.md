# Release check 1.4.2 (post-release): full bench vs v1.4.1

**RESULT: NO REGRESSION by the release gate (Haiku PASS, Luna PASS).**

**Caution on Luna:** the pass-rate point estimate is -5.5 points (42/110 vs
48/110), past the -5 point warning line the harness prints. It is not
significant (McNemar p = 0.418; interval [-14.5, +3.6] points), so the gate
passes, but the data cannot exclude a Luna loss of up to 14.5 points.
Haiku shows no change (103/110 in both).

Raw command verdict: `INCONCLUSIVE (gate passed on an off-target set)`; the
command exits nonzero on this set by design, as in [1.3.1](1.3.1.md).
`ALLOW_OFF_TARGET=1` was set. This is the first full bench of the 1.4 line;
1.4.0, 1.4.1 and 1.4.2 had run only the 10-task smoke.

## Luna diagnosis

**VERDICT: NOISE. Nothing Luna receives or runs under differs between
v1.4.1 and v1.4.2.** In 8 captured trials, the Codex command line (apart
from per-trial paths), the reasoning effort, the base instructions, the
developer message, the Aether task message and the tool list were
byte-identical across the two arms. No trial compacted. The drop is sampling
variance of Luna at low effort. No fix is proposed.

### Captured trials (4 tasks, 1 per arm)

Method: the 4 strongest-losing tasks of the subsample grid were picked:
`protocol-4` (longctx), `exporters-1` (refactor), `diff-1` (algo) and
`ledger-9` (traceback). They ran once per arm on `luna/old` and `luna/new`
(8 trials, `--jobs 2`, low effort, 600 s), from a 4-task copy of
`bench/release-set/v2` whose task hashes match the original. The binaries were
the published v1.4.1 and v1.4.2 x86_64 musl archives, verified against each
release's `SHA256SUMS`. Codex 0.169.0 ran in a private HOME holding mode-600
copies of the two credential files, deleted afterwards. A watcher read each
sandbox process's `/proc` argv. The Codex rollouts and Aether stores were
then compared.

| Task | Old | New | Turns old / new | Tool calls old / new | Compactions | Peak input tokens old / new | Total tokens old / new | End (both) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| diff-1 | pass 10/10 | pass 10/10 | 1 / 1 | 6 / 12 | 0 / 0 | 18,160 / 21,395 | 112,107 / 229,891 | `task_complete`, completed |
| exporters-1 | pass 6/6 | **fail 5/6** | 1 / 1 | 3 / 6 | 0 / 0 | 17,400 / 18,195 | 64,009 / 114,210 | `task_complete`, completed |
| ledger-9 | pass 11/11 | **fail 7/11** | 1 / 1 | 7 / 6 | 0 / 0 | 19,583 / 17,671 | 134,909 / 113,669 | `task_complete`, completed |
| protocol-4 | pass 5/5 | pass 5/5 | 1 / 1 | 10 / 8 | 0 / 0 | 42,966 / 42,967 | 382,782 / 300,698 | `task_complete`, completed |

- **Command line.** Both arms ran the same `codex app-server -c
  agents.enabled=false -c features.multi_agent=false -c
  model_reasoning_effort="low" -c mcp_servers.aether.*` command (24 argv entries)
  with the same `shell_environment_policy.set.*` overrides. The only
  differences were the per-trial values: paths, the agent id, the socket and
  the bridge token.
- **Effort.** Every Codex `turn_context` says `effort: low`, model
  `gpt-6-luna`, window 258,400. The v1.4.2 store records
  `effort_requested` and `effort_effective` as `low`; v1.4.1 records `effort:
  low`.
- **First turn.** The base instructions, the developer message and the
  `additional_tools` payload (`exec`, `wait`, `request_user_input`,
  `request_user_input_async` and `sleep`) hash identically in all 8 trials.
  Neither arm's rollout lists an Aether MCP tool. The Aether assignment
  message is byte-identical per task after normalising ids and the nonce. The world state
  is identical except one Codex-side connector entry
  (`mcp__codex_apps__search_service`). It appeared in 3 sessions (2 old, 1
  new), so it does not follow the arm.
- **Run shape.** Each trial ran one turn and ended by finishing its turn. No
  trial hit the timeout, the spend guard or a compaction. Peak context was at
  most 43K of 258K tokens, so compaction thresholds cannot matter on these
  tasks. All tool calls were `exec_command` and `apply_patch`; no trial
  called an Aether tool.
- **Outcome.** Old 4/4, new 2/4. The two new-arm failures followed the same
  inputs, so they come from the model's sampling, not from Aether. The new arm
  even used more tool calls on the tasks it failed. Codex quota stood at 81 %
  of the weekly window throughout, with no rate limiting.
- Spend: about USD 0.035 API-equivalent, 1.45M tokens.

### Suspected causes, ranked

1. **Sampling noise (most likely; supported).** The inputs were identical, and
   the source diff shows no change to what a Codex agent receives. Luna at low
   effort sits near a 40 % pass rate, with 38 of 110 pairs disagreeing in a
   single run. Its outcomes vary a lot between trials of the same input, and
   the per-task grid shows tasks flipping between repeats in both arms. The
   full bench (22/16, p = 0.418) and the subsample (21/11, p = 0.110) are both
   non-significant. The 8 trials here (2/0 discordant) add no evidence of a
   systematic effect.
2. **Codex backend variance over time (possible; arm-neutral).** The
   server-side connector list varied between sessions, and the account sat at
   81 % of its weekly quota. The bench interleaves old and new in each block,
   so such drift falls on both arms equally and cannot explain a gap by
   itself.
3. **The 1.4.2 `list_models` and `inspect_state` output changes (ruled out
   for the losing families).** They reach Luna only through a tool call that
   solo tasks do not make. The one family that delegates, `delegation`, scored
   100 % in both arms.

### Proposed fix

No code fix. Nothing in `crates/aether-engine`, `crates/aether-model`,
`crates/aether-context` or `crates/aether-runtime` changes Luna's launch,
instructions, tools, effort or compaction point between v1.4.1 and v1.4.2, so
there is nothing to revert. Keep the release per the operator's rule. If a
future Luna comparison needs more confidence, the cheapest lever is
statistical, not code: run the Luna arms at `REPEATS=3`.

### How to verify

- Re-run the claim's premise on any Luna trial pair: `codex-argv` capture plus
  rollout hashes, as above. A real Codex-path regression would show up as a
  differing argument, effort, instruction hash or tool hash. These 8 trials
  show none.
- To bound the pass-rate effect itself, run `make bench-release ARMS=luna/old,luna/new
  REPEATS=3 ALLOW_OFF_TARGET=1` on the full 110-task set (660 trials, about USD
  5 and 2.5 hours at `JOBS=6`). A true loss of 5 points or more would show as
  a one-sided interval below zero. No-difference would put the interval
  around zero with a half-width of about 6 points.
