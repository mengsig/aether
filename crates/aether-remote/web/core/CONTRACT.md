# Remote browser boundary

`index.js` exports `createTransport(options?)`, synchronous `createStore(transport, options?)`, and `createCommand(store, transport)`. The store owns connection subscriptions, durable recovery, normalized snapshots, event projection, and drafts. `dispose()` releases its listeners. Production modules never import `dev/` or Node dependencies.

The authoritative specification is `docs/remote.md`, protocol **18**, introduced by contract commit `6dae3c38`, with authorization/schema updates from `fb7b0922` and host services from `9ee6bb11` and push/schema updates from `cdb9ec5e`; submission lookup and permanent uncertainty follow `3ee63eba`. Wire assumptions are isolated in `contract.js`, `host.js` and `permissions.js`; the earlier provisional ticket-based endpoints have been removed.

## Authentication and pairing

Pairing calls `POST /api/pair/claim` with `{code,device_name,public_key}`. The public key is the 65-byte raw P-256 point encoded as unpadded base64url. The returned fingerprint must equal the browser's own SHA-256 public-key fingerprint. `pair(code,name,onProgress?)` reports `{phrase,fingerprint,state}` while polling `/api/pair/status` once per second. Enrollment requires the host's confirmation. Polling stops at the server expiry (with a five-minute local ceiling), on terminal rejection, or when `disconnect()`/`forget()` aborts it. Requests have a 15-second HTTP timeout, implemented with AbortController and cleaned-up timers/listeners for Safari 16.4 compatibility. No code goes in a query string.

The device's nonextractable P-256 private `CryptoKey` is stored by IndexedDB structured clone, scoped to origin. It is never exported or copied to localStorage. The enrolled device ID and daemon identity live alongside it. Private browsing/storage failures remain visible.

Every connection opens `/ws` with subprotocol `aether`, waits for `{frame:"challenge",nonce,instance_id}`, then sends `hello` with an ECDSA/SHA-256 signature over exactly five newline-separated fields: `aether-remote-auth-v1`, instance, origin, device ID, nonce (no trailing newline). Signatures are unpadded base64url IEEE P1363. The first successfully authenticated welcome pins the instance. A changed pinned instance halts reconnect and requests verification/re-pairing rather than signing for a different store. Re-pairing to a different instance discards cached state and old outbox targets. Role and device name come from the authenticated `Welcome.device`, not a local role preference.

Hello uses version `1.0.1`, protocol 18, and features `deltas` / `artifact_bytes`. `clientName` may override the informational client name; default is `aether-web` in a page and `aether-web-sw` in a worker.

## Protocol and authorization

Outgoing frames are `{...command,req}`. Replies are `{frame:"reply",id,result:{Ok:{reply,data?}}}` or `{frame:"reply",id,result:{Err:{code,message}}}`. A command's own `id` cannot overwrite correlation. Event sequences and request IDs must be safe JavaScript integers; unsafe u64 values fail visibly rather than round. Text frames and outgoing commands are capped at the documented 64 MiB. Malformed frames terminate the connection. Late mutation replies on the same connection retire their recovery records; late read replies are ignored. At most 128 requests may be pending; request timeout is 20 seconds.

Authorization mirrors the remote matrix. Reads use an explicit allowlist. Filesystem completion, git summary, and workspace validation are operator-only reads and never produce mutation receipts. Unknown commands require operator role; host-only commands and global approval-rule creation/resolution are refused locally. `mcp_servers refresh:true` requires operator; reading does not. `list_devices` is operator-only and excludes revoked devices and key fingerprints; revoking, renaming, and re-roling remain host-only. Device-self push operations are permitted for observers too. Remote requests cannot grant allowed paths or repository identity, change existing agent backend/tools, or spoof trigger sources. Host and parent ceilings still govern approval/network settings. Server enforcement remains authoritative.

`listWorkspaces` retains `{path,name,exists}`; missing directories are shown disabled. `listDirectory` / `searchFiles` return `{entries,truncated}` backed by `complete_path`, so incomplete results ask the operator to refine the prefix. Paths are limited to 4096 UTF-8 bytes without control characters. `gitStatus` retains repository/detached/head/branch/root and optional change/upstream counts; absent counters remain unknown. An `unavailable` Git response allows workspace validation to continue and displays “Git status unavailable”. Host Git status supports content-filter repositories, including Git LFS. Other errors remain failures. `listDevices` returns `id,name,role,revoked,createdAt,lastSeenAt,current`. `pushStatus` maps `get_push_config` to `enabled,subscribed,publicKey`; push subscription keys are flattened from browser `toJSON()` into `{endpoint,p256dh,auth}`.

## Delivery and durable recovery

Every mutating `transport.request` emits a receipt lifecycle. Page transports attach the store to persist it, including calls made outside `createCommand`; the service worker’s unkeyed push renewal instead reconciles through its acknowledgement and `get_push_config`. The pending receipt, with exact command fields, is persisted **before socket transmission**. A failed durable write prevents sending. A server receipt marks it sent/failed and removes its durable recovery record; timeout or connection loss marks it unknown. Successful replies remain available as `Outbox.reply` only in memory for the current UI session. Reload converts persisted pending receipts to unknown. Failure to persist a received receipt is reported while preserving the known result in memory; reload conservatively sees the previous unresolved receipt.

The browser generates an idempotency key for every command that declares one: `create_agent`, `create_task`, `send_message`, `reply_to_question`, `trigger`, `create_schedule`, `resolve_approval`, `restart`, `cancel`, `interrupt`, `pause`, `resume`, `archive`, `update_agent`, `set_approvals`, `update_schedule`, `create_memory`, and `add_approval_rule`. An explicit retry preserves the key, exact command, first-send `horizon`, and `createdOrder`, and stores each wire attempt separately under the same logical receipt. Nested command fields are cloned before persistence and transmission. Commands without a declared key do not receive an invented field.

Receipt retention is bounded: the daemon may evict receipts before seven days under load. A retained key returns its original receipt; changing its payload conflicts. After eviction a retry can repeat work, so the UI asks the operator to inspect current state before retrying and never promises indefinite duplicate protection.

`custom` events named `submissions.evicted` mark all unresolved keyed receipts with a durable inspection warning: the event gives a count and oldest time, not affected keys, so the browser cannot identify a safe subset. Generic retries refresh live state before explicit confirmation; uncertain messages refresh their transcript first. Operators must inspect the affected resource. `remote.restricted` preserves event continuity while displaying only the host restriction. Resolved agent inbox deliveries retain optional `by: Actor` and show who decided alongside the original record.

Protocol 18 `Welcome.submission_horizon` is the capability signal for read-only `resolve_submission`. Missing capability never triggers a lookup. Each first send saves the latest held opaque horizon (or null) with the exact original keyed command. Same-instance reconnect checks unresolved records sequentially in creation order with `{cmd:"resolve_submission",command:original,horizon?}`. The outer read never receives a key or creates an outbox row; it requires the original command's authority and device namespace.

`submission_resolved` with `outcome:"executed"` supplies the exact original success reply and retires the record without sending again. Only `outcome:"absent_safe"` for an entry never marked unconfirmed authorizes automatic resend of the exact original command and key. `unknown` (`no_horizon`, `foreign_horizon`, `horizon_ahead`, or `forgotten`) and resolver errors leave delivery unconfirmed for explicit operator review. A healthy-socket mutation timeout starts lookup immediately. A lost lookup closes its connection and retries through bounded reconnect backoff. Missing capability, an unknown outcome, or an actual resolver error permanently latches `Outbox.unconfirmed` with its reason and explanation. Separate monotonic markers preserve this latch across reloads, stale writes and tabs. A later `absent_safe` never clears it; `executed` still retires the entry. Lookup connection loss does not latch uncertainty. Explicit Send again records its decision and sends once; if its acknowledgement is lost, the original horizon and uncertainty remain. Reply horizons update only later new records; existing records retain their first horizon. The client validates the RFC3339 shape of `retained_since` but never compares it or interprets horizon contents.

`store.resolvePendingSubmissions()` provides a coalesced lookup pass. Requests interrupted during a pass queue a subsequent pass for those IDs only; explicit unknown/error results are not repeatedly queried in that connection epoch. A new welcome rechecks all unresolved receipts in creation order. `Outbox.recovery` is `resolving`, `unsupported`, `unknown`, or `error`; `error` retains a useful explanation. The UI can hide operator choices during first resolution. A latched unconfirmed entry retains its explanation and explicit mark-delivered, send-again, and discard choices even while a later read-only lookup runs. Confirmed `await store.dismissReceipt(id, "delivered" | "discarded")` removes a reviewed receipt durably and records the distinct choice atomically in its retirement marker; pending commands cannot be dismissed. Incidental array eviction cannot delete unknown receipts. A sent receipt is not removed by matching message text; its exact `reply` is available for stable identity correlation or a collapsed recent-deliveries section.

Cross-tab exclusion applies only after all participating tabs have loaded this implementation; older open tabs must be reloaded. Browser operations use `navigator.locks.request` in exclusive mode with a name containing the daemon instance, authenticated device, and logical submission key. An ordinary mutation holds this lock from durable preflight through acknowledgement or uncertain settlement. Recovery requests the same lock with `ifAvailable:true`, reads the durable entry and permanent uncertainty again, then holds it through lookup, uncertainty persistence, automatic resend, and settlement. A busy entry is left alone while the pass continues with later entries. Busy IDs share one one-second retry timer; there is no immediate retry loop. Disconnect, a new session, and disposal clear that timer. Storage events introducing another tab’s pending wire trigger a targeted pass, so the surviving page can recover after a holder closes without waiting for a new Welcome. Explicit Send again, late replies, and dismissal use the same lock and reread the durable state after acquisition. Manual Send again and dismissal wait at most three seconds for acquisition, then reject with “Another tab is still working on this delivery”; the cancelled request cannot run later. Their preflight/decision reads occur after the lock is granted, so an earlier UI confirmation does not authorize a stale receipt. A competing lookup cannot start or write uncertainty between another tab’s final latch read and wire send. Terminal markers and wire-specific failures remain authoritative after waiting.

Recovery passes an internal, frozen `RequestOptions.submissionLock` lease to its nested mutation and receipt callbacks. Active ownership and the exact scope/key are checked; expired or foreign leases are rejected. This explicit reentrancy avoids reacquiring a lock already held by recovery. Mutation frame listeners may return `Promise<void>` and are awaited before transmission/settlement. Queued recovery and manual sends are cancelled on connection/session changes; connection, role, scope, and authority are checked again when granted. Dismissal returns `Promise<void>` and its errors must be awaited by the UI. `patch({outbox})` updates the display only; durable receipt writes require the internal lease and affect only its one logical key. Session refreshes cannot checkpoint stale receipt states over a lock holder. Retention warnings also acquire each affected receipt’s lock.

When Web Locks is absent, automatic replay is disabled. If its request API rejects before entering the callback, it stays disabled in that page until reload. Busy locks and cancellation are handled separately; an error from a receipt or persistence callback never disables the API or reruns that callback. Without Web Locks, ordinary sends and explicit Send again still use durable preflight, but there is no cross-tab exclusion guarantee. Read-only lookup may retire an executed entry. Unresolved entries are permanently marked unconfirmed with reason `locks_unavailable` before lookup, and `absent_safe` **never** causes automatic resend. The user must explicitly choose Send again; its original payload, key, horizon, and permanent uncertainty are retained. No local mutex or storage lease is substituted for Web Locks.

Cross-tab checkpoint writes cannot replace another tab's ledger. Separate permanent retirement markers dominate stale ledger writes: sent/dismissed markers apply to the logical key, while failed markers apply only to the exact wire send identity. A later rejected attempt cannot prove that another outstanding attempt failed; any remaining attempt keeps the logical receipt unconfirmed. Wire ordinals select display rows only and never establish retirement authority. Late original errors do not downgrade a confirmed success or retire a newer wire attempt. Storage events retain transient terminal rows for the original request's promise lifetime.

The checkpoint is written before a newly pending ledger entry. That entry is the last fallible persistence operation before its in-memory receipt is published and the socket is called, so failed preflight persistence cannot leave an invisible command eligible for automatic recovery. Request failures belong to the receipt and calling UI; the global workspace error is reserved for failed accepted-command refreshes and state synchronization failures.

A bounded localStorage checkpoint atomically persists `{instance,device,last_seq,activity,attention}`. Receipts use separate keys scoped by instance and device: checkpoint writes never replace the ledger, so a stale tab cannot erase another tab’s pending command. Storage events refresh the visible ledger. Forgetting clears local state and disconnects other open tabs. Event sequence advances only with successful validated projection and persistence. Agents and transcripts are refreshed from authoritative reads; they are not persisted. Same-instance reconnect subscribes after the applied cursor, deduplicates old events, refreshes `list_agents` and authoritative `get_attention`, and reconciles loaded transcripts after their last held entry. An initial fetch remains incomplete until its authoritative response arrives; live rows cannot advance that initial cursor. A failed conversation refresh reports its agent and retains held rows without blocking fleet resynchronization. Attention includes pending approvals/questions and failed/blocked agents.

A missing or expired cursor uses `subscribe after:null`, buffers live frames, reads snapshots, commits the subscription baseline, then applies buffered events. An ID-zero daemon diagnostic requests the same resync after reconnect. Buffer overflow fails visibly. Snapshot refreshes coalesce, perform at most two immediate passes, and defer sustained churn. Transient streams clear on disconnect; deltas are never replayed.

Reconnect starts around one second, doubles with jitter, and caps at 30 seconds. `4401` stops; `4403` reconnects so a changed role can take effect (a revoked key is then refused); `4503` uses the maximum backoff. A displaced or idle `4408` connection preserves pairing and reconnects with backoff. A hello rejected with `unavailable` because all device connections are occupied also preserves pairing, retains an explicit capacity explanation, and retries with a longer initial delay. An idle-aware `ping` command keeps subscriptions alive. A malformed protocol or locally rejected frame size stops with a visible error.

## Bounds and limitations

The checkpoint has a 2,000,000-character bound, with 500 activity records and 1,000 attention records on restore. New sends are limited to 100 logical receipts, 256 unresolved wire attempts, and 2,000,000 UTF-8 bytes across all unresolved wire records. These limits are checked before persisting a pending attempt or sending bytes. Concurrent tabs may briefly exceed the soft limits; further sends are refused while existing receipts remain readable and can be reconciled. Receipt loading retains a separate hard 1,000-attempt corruption guard. Settled receipts may be evicted; unresolved receipts are never silently evicted, and a full unresolved ledger blocks further mutation. Retirement markers reserve room for pending work and stop new sends at 20,000 markers per daemon/device scope. They are never aged out: the visible capacity error asks the operator to reconcile pending work, then forget and re-pair to clear local history. Draft persistence is separate: 50 agents, 20,000 characters per draft, 200,000 serialized characters total, oldest evicted first. Storage errors leave prior draft contents intact and are returned to the caller.

All loaded transcript rows are retained for search and virtualization; the cache evicts entire least-recently-loaded agents above 20 and re-fetches them when opened. Only opened/loading agents allocate transcript cache; live messages from unrelated agents cannot evict the active conversation. There is no silent transcript row truncation. Live streams are limited to 100 agents and 2,000,000 characters per text/thinking field; crossing the limit fails visibly and asks to reload the full transcript. Full-resync buffering is capped at 10,000 frames.

The browser cannot safely represent protocol integers above `Number.MAX_SAFE_INTEGER`, and intentionally refuses them. A pairing abort after host enrollment may leave a harmless enrolled public-key record on the host; removal requires host administration.

## Development server and validation

Run `node dev/server.js` from `web/` (`PORT`, default 4173). It binds 127.0.0.1. Demo codes: `aether-demo` (operator), `aether-observer` (observer); `PAIR_SECRET` overrides the operator demo code. State is ephemeral. The mock uses real P-256 proofs, matching-origin requests, the required `aether` subprotocol, and the exact protocol envelopes. It intentionally auto-confirms the simulated host after 1.5 seconds; `MOCK_AUTO_CONFIRM=0` leaves confirmation to Node tests via `server.auth.confirm(pairing,accept)`.

HTTP serves public assets under CSP, nosniff, no-referrer, and no-store; it restricts host/origin, private paths, traversal, and symlink escapes. Mock-only commands `mock_disconnect` and `mock_malformed` exercise failure handling. `mock_drop_reply:true` commits a mutation and loses its receipt. `mock_submission_fault` configures one-time precommit or lookup loss (`drop_mutation`, `drop_lookup`), lookup rejection (`reject_lookup`), receipt eviction (`forget`), and capability absence (`enabled:false`). The mock advertises submission lookup by default; tests can explicitly disable it for older-daemon compatibility. None is imported by production code. Push is explicitly unavailable in the mock.

Dev-only dependencies are `ws` 8.18.3, `@types/ws` 8.18.1, and Ajv 8.17.1. `dev/protocol.schema.json` is the copied generated protocol 18 schema. The mock validates incoming commands and outgoing replies against it, and tests validate fixtures, mutations, and broadcast events; production loads no schema or validator. Run `node --test core/*.test.js` and the page, Node, and service-worker TypeScript checkJs configurations. Tests cover signatures/origin/replay, authorization, correlation, uncertain writes, persisted reload, expired-cursor resync, draft bounds, static-server security, and schema-valid fixtures. Lock regressions cover a deterministic pause after final preflight and before wire, queued retry cancellation and terminal rereads, stale/foreign leases, missing/rejected Web Locks, bounded manual waits, progress past busy keys, and timer cleanup. Playwright also exercises two real pages in one browser context with shared localStorage and native Web Locks, including permanent uncertainty observed before and during competing recovery, a held unknown reply, and a holder page closing before transmission while its peer remains connected.

## Push payloads

`ui/push.js` validates version, pinned instance, safe sequence, timestamp, known kind and the required `PushPayload.url`. It accepts only the documented approval/question/agent/activity fragments and verifies the target against payload IDs. Notification clicks use the supplied validated URL, with activity as the fallback for an invalid stored route. Display tags coalesce by instance, agent and attention/status class; the daemon owns provider-level pacing and acting-device exclusion. Agent names and previews retain Unicode code points within the 80/200-character limits.

Settings surfaces the daemon's endpoint-policy error without replicating its configurable host allowlist. Failed test delivery refreshes push status, showing a subscription removed on 404/410; the error explains how to renew an expired browser subscription. The mock remains explicitly push-disabled. Tests cover payload schema, all seven route kinds, unsafe links, coalescing, rejected endpoint messages and dead-subscription status. Actual delivery through browser push services still requires device acceptance.
